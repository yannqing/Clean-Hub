# POS 收银前置条件与测试数据修复

创建租户与开放收银是两个步骤。新建租户必须选择国家，并存在 SaaS 已配置、启用且完整的国家税务模板；服务器将国家保存为模板对应的 ISO 两位代码，同时初始化模板和币种。税务登记号可以在创建后填写，但未填写时不能结款。

SaaS 租户详情与租户首页使用同一份服务端就绪检查。一个可营业的门店须同时具有有效店主、可销售的目录、已绑定终端、与模板一致的币种和完整的税务配置；不能把甲店的目录和乙店的终端拼成“已就绪”。经理只能看到自己有权限的门店。

税务配置是租户级政策；付款校验只检查当前门店。其他门店的币种问题会在对应门店显示，不阻止正常门店应用模板、同步或结款。服务和商品目录也按当前门店币种筛选，避免把 CNY 价格当作 XOF 价格使用。

Android 初始化和 PIN 登录会提示缺少的税务条件。登录后仍可查看工单、历史订单和设置；付款入口、购物车内的付款按钮与最终收款按钮在税务未就绪时禁用，本地付款命令和 API 另有独立校验。提示明确说明后台缺项不会因点击同步而自动修复。

完整同步必须读取当前终端的收银设置和税务状态。税务验证缓存沿用终端的八小时有效期；配置缺失、过期、时间在未来或重新绑定到另一门店时，结款暂停。修改本地打印偏好不会延长税务验证有效期。有效缓存允许既有现金离线流程；终端断网时不能即时得知平台刚发生的修改，联网后会重新检查。已有离线命令保持原值，拒绝回放时进入既有异常处理流程，不自动重算已经收取的现金。

## 全新开发环境

1. 执行 `pnpm db:migrate`。
2. 执行 `pnpm db:seed`。仅本地开发数据库默认允许执行；不要用完整 seed 修复线上账户。
3. 开发 seed 从现有首发配置 JSON 导入数据库中缺少的模板。已完整配置的模板不会被覆盖；未被租户选用的旧空壳模板才会补齐。业务代码和初始化 SQL 均从数据库模板读取税率和分项。
4. `dev-accounts.sql` 给 CLEAN-001、CLEAN-002、CLEAN-003 设置 SN、CI、ML 测试国家。`demo-tax-settings.sql` 从数据库模板初始化租户设置、税务登记号、默认税率、分项和税类；税号带 `TEST-` 标识，只用于测试。
5. 整个 seed 在一个事务内执行。缺少可用模板或测试门店币种冲突时，会明确报错并回滚。

国家模板 JSON 属于一次性配置资料，不是运行时法定税率常量。真实商户仍须由 SaaS 管理员通过平台表单或文件上传复核配置，并使用真实国家与税务登记号。

## 已确认的历史测试租户

只对脚本中固定 ID、编码和名称均匹配的四个测试租户开放修复。默认命令只预览；实际应用需要明确指定参数：

```bash
pnpm --filter @cleanhub/api repair:demo-tax-readiness
pnpm --filter @cleanhub/api repair:demo-tax-readiness --apply-confirmed-demo-data --prepare-new-demo-branch
pnpm --filter @cleanhub/api check:tax-readiness
```

脚本在单个事务内补缺失的租户设置、国家、模板和 TEST 税号，并记录操作者、前后配置及修复原因。现有租户币种与模板不同会中止；不会猜测实际汇率或修改既有金额。对仅有其他币种旧门店的已确认测试租户，额外建立模板币种的新测试门店，复制目录为带 TEST 名称的新服务和独立测试价格。原门店、原价格和历史订单逐项校验保持不变；任一校验失败则全部回滚。

数据备份保存在操作者本机私有目录，修复日志含完整前后配置。应用代码和 APK 需要随后按正常发版流程部署；数据修复不会替换线上程序。部署顺序为 API、管理端／POS Web，然后新版 APK。旧原生 APK 可以读取服务端扩展后的税务状态。

数据库的旧可空国家字段暂保留兼容性，创建 API 与初始化 SQL 已禁止新租户缺少国家。任何额外导入或直接 SQL 写入后都应运行就绪检查；对真实历史租户完成资料核实之前，不通过默认国家或税号强行补齐，也不执行会阻止历史整改的全表非空迁移。

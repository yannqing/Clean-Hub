# CleanHub POS 硬件支持与试点发布说明

## 1. 适用范围

本文记录 `complete-pos-phase1` 当前可验证的 POS Web/Desktop 硬件边界、试点准入条件、发布步骤和回滚步骤。支持结论以实际 UAT 结果为准，不得把尚未测试的品牌或型号对外标记为已支持。

## 2. 当前支持清单

| 类别 | 当前接入方式 | 支持状态 | 已认证型号 |
| --- | --- | --- | --- |
| 小票/标签打印机 | Desktop 调用操作系统打印机；T1101 原生 Android 应用可调用内置打印机，或连接系统已配对的 Bluetooth SPP / ESC/POS 打印机 | 可进入试点 UAT | POS-T1101 内置打印机；外接具体型号仍待门店 UAT |
| 扫码枪 | POS Web 扫码页接收 USB HID 键盘模拟输入 | 可进入试点 UAT | 暂无；具体型号待门店 UAT 后登记 |
| 原生扫码适配器 | Desktop preload 已保留类型化 scan 事件边界 | 默认不可用，需单独配置适配器 | 无 |
| 钱箱 | Desktop preload 和主进程已保留授权开箱命令边界 | 默认不可用，试点必须配置专用适配器 | 无 |

“已配置”只表示后台存在 active 硬件配置，不表示设备实时在线。POS 必须以 Desktop capability discovery 和具体命令结果判断当前可用性。

## 3. 试点硬件准入

### 打印机

- 操作系统中能稳定识别设备，并已安装厂商正式驱动。
- Electron `getPrintersAsync()` 能返回与后台配置一致的打印机名称。
- 支持试点使用的纸宽，并完成中文、英文、法文字符和金额打印检查。
- 连续打印、缺纸、断电、驱动离线和恢复后的重试均通过 UAT。

当前打印路径使用系统驱动打印，不等同于直接 USB/Bluetooth ESC/POS 协议兼容。`packages/hardware` 提供通用文本与 ESC/POS 模板能力，但未经过 UAT 的机型不得宣称支持。

T1101 原生 Android 应用的蓝牙路径直接使用 Bluetooth SPP 发送 ESC/POS 数据。打印机必须先在 Android 系统完成配对，再由管理员在 Tenant 后台创建逻辑设备，并在 POS 设置中测试、绑定和选择默认用途。列入列表和测试成功只证明基础链路可用；纸宽、字符集、二维码、断电恢复和长时间稳定性仍须按具体型号完成 UAT。

### 扫码枪

- USB HID 键盘模拟模式能在 POS 扫码页完整输入订单码并发送结束键。
- 连续扫描不会丢字符、重复提交或导航到错误门店数据。
- 前缀、后缀、键盘布局和字符集按门店环境固定并记录。

原生串口、蓝牙 SDK 或厂商协议扫码当前没有可用适配器；仅存在类型化扩展边界。

### 钱箱

- 试点前必须实现并配置与实际连接方式匹配的钱箱适配器。
- 必须验证 `getCapabilities().cashDrawer === true` 后才允许现场验收。
- 手动开箱仅 Owner/Manager 可见，必须填写原因，并先通过 API 授权后再调用 Desktop bridge。
- Cashier 直接调用授权 API 必须返回 `FORBIDDEN`。

默认 Desktop 运行时使用 unavailable adapter，因此没有完成适配和 UAT 的钱箱不能纳入试点支持清单。

## 4. 试点发布步骤

1. 固定一个 tenant、一个 branch、一台已登记 terminal 和一组待测硬件，记录操作系统、驱动版本、连接方式、设备品牌、型号和序列号。
2. 完成 POS 终端登记、门店绑定和凭据轮换验证，确认 PIN 会话包含正确 terminal/branch。
3. 在操作系统中安装打印机并完成系统测试页；在 CleanHub Desktop 中确认 capability 和打印机列表。
4. 验证收据号、订单展示码、项目、金额、支付方式和多语言内容；模拟首次失败后以同一打印任务 ID 重试，确认不产生重复成功记录。
5. 以键盘模拟模式验证订单码扫描、连续扫描、错误码和跨门店拒绝。
6. 仅在钱箱专用适配器通过 capability 检查后，由 Manager 填写原因执行手动开箱；核对 actor、terminal、branch、reason 和 authorization ID 审计字段。
7. 执行缺纸、打印机离线、扫码枪拔出、钱箱断开、Desktop 重启和网络中断场景，确认 UI 显示真实失败且任务可重试。
8. 将通过 UAT 的品牌、型号、驱动版本和固件版本补充到本文件“已认证型号”列，经发布负责人签字后才扩大部署。

## 5. 试点观察与支持信息

每次硬件故障至少记录：tenant、branch、terminal、操作人、时间、设备型号、驱动/固件版本、连接方式、打印任务 ID 或授权 ID，以及 Desktop/API 返回的原始错误。不得用“已打印”“已开箱”等成功提示覆盖实际失败。

打印失败任务保留 `pending/printing/failed/printed` 状态、尝试次数和最后错误；重试沿用原任务 ID 与幂等键。支持人员不得通过重复新建任务来掩盖失败任务。

## 6. 回滚步骤

1. 停止该门店新交易，完成当前订单、班次和离线队列检查。
2. 在后台将问题硬件配置设为 inactive，保留配置和审计记录，不删除历史数据。
3. 钱箱故障时停用手动开箱入口并恢复门店人工现金管控；不得放宽 Cashier 权限或跳过原因校验。
4. 打印故障时切换到已验证的系统打印机；未完成的打印任务保持 failed/pending，恢复后使用原任务 ID 重试。
5. 扫码故障时回退到 POS 扫码页手工输入，不启用未经验证的原生适配器。
6. 如需回滚 Desktop/POS 版本，保留终端登记、HttpOnly 凭据、服务端授权、审计和队列数据；不得恢复未登记终端登录或前端直连 Node API。
7. 回滚完成后复测登录、门店隔离、现金收款、打印失败提示和交班，再恢复营业。

## 7. 发布结论

当前可用于受控试点的是“操作系统打印机 + USB HID 键盘模拟扫码枪”能力，具体品牌和型号仍待实机 UAT。原生扫码和钱箱默认不可用；钱箱只有在专用适配器、权限审计和故障场景全部通过后才能加入已认证清单。

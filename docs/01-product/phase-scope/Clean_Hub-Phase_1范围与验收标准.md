## 1. 文档目的

本文档用于明确 CleanHub **Phase 1：商业试点版** 的交付范围、暂不交付范围、待确认边界和验收场景。

Phase 1 的核心目标不是一次性交付 CleanHub 完整平台，而是优先完成一个真实门店可以正式营业的最小闭环：

**客户识别 -> 收件下单 -> 计价 -> 收款 -> 打印 -> 生产状态追踪 -> 通知/取件 -> 财务日结。**

> **说明：范围口径**  
> 本文档是产品总 PRD 的阶段拆分文档。若本文档与总 PRD 存在冲突，以本文档对 Phase 1 的范围定义为准。

## 2. Phase 1 目标

### 2.1 业务目标

Phase 1 需要支撑首个试点门店完成真实营业。系统上线后，门店员工应能在不依赖纸质主流程的情况下完成客户接待、收衣、收款、打印、状态更新和取件交付。

### 2.1.1 终端边界

Phase 1 的门店正式收银入口应按 **Desktop Shell + POS Client** 理解。`pos-web` 是门店员工 POS 界面，`desktop` 是 Windows/macOS 正式运行壳，负责本地硬件、离线运行和桌面能力。

`mobile` 不作为 Phase 1 默认收银员 POS。移动端优先按**客户侧 / 配送侧**理解，例如客户预约、订单状态、通知、配送任务、GPS、拍照、签收和便携蓝牙打印。若 Phase 1 需要 Android 初版，应单独确认它是客户/配送最小入口，还是仅做技术壳预留。

### 2.2 产品目标

- 建立 CleanHub 的基础多租户和门店模型。
- 完成 POS 端核心收银与收件闭环。
- 完成基础后台配置能力。
- 完成基础打印、扫码、钱箱等硬件接入。
- 完成现金和基础移动支付记录能力。
- 完成基础订单状态流转和基础报表。
- 为 Phase 2 的完整离线、多门店、会员、B2B、客户移动端、配送移动端和库存能力预留架构。

### 2.3 成功标准

| 维度 | Phase 1 成功标准 |
| ---- | ---------------- |
| **营业闭环** | 门店可以完成从新客户下单到客户取件的完整流程。 |
| **收银闭环** | 现金支付、移动支付记录、待确认支付和基础日结可以正常使用。 |
| **打印闭环** | 小票、衣物标签或袋标签能够按确认模板打印。 |
| **状态追踪** | 订单可以从已收件流转到处理中、就绪、已交付。 |
| **基础管理** | 管理员可以配置租户、门店、员工、服务、价格和基础硬件。 |
| **可实施** | 技术员可以按照标准步骤完成门店安装、账号配置、硬件测试和基础培训。 |

## 3. Phase 1 必须交付范围

### 3.1 平台与租户基础

Phase 1 需要支持平台方创建和管理试点租户，并为租户分配唯一的 `Pressing Code`。

必须交付：

- 创建租户。
- 编辑租户基础信息：名称、国家、城市、默认语言、默认货币、联系人。
- 分配和展示 `Pressing Code`。
- 租户启用/停用状态。
- 基础租户隔离：所有业务数据必须归属到 `tenant_id`。
- 平台管理员进入租户进行基础排查的能力可以预留，但敏感代操作必须记录日志。

不要求 Phase 1 完整实现：

- 完整 SaaS 订阅计费。
- 套餐自动扣费。
- 多币种平台收入结算。
- 平台级复杂 BI。

### 3.2 门店与基础配置

Phase 1 需要支持至少一个租户下配置一个真实门店。

必须交付：

- 创建和编辑门店。
- 配置门店名称、地址、电话、营业时间、默认语言、默认货币。
- 配置基础小票信息，如门店名称、电话、地址、Logo 预留。
- 订单、支付、员工操作需要归属到门店。

不要求 Phase 1 完整实现：

- 多门店经营对比。
- 跨门店库存调拨。
- 跨门店客户复杂权限。

### 3.3 用户、角色与权限

Phase 1 需要支持门店营业所需的基础角色和权限。

必须交付：

- 创建员工账号。
- 支持基础角色：Super Admin、Owner、Manager、Cashier。
- 员工启用/禁用。
- 密码或 PIN 登录。
- 基础分店绑定。
- 基础权限控制：普通 Cashier 不能删除订单、不能退款、不能修改关键配置。
- 敏感操作记录审计日志：删单、改价、退款、重印、打开钱箱、用户禁用。

不要求 Phase 1 完整实现：

- 细粒度按钮级权限配置后台。
- 复杂审批流。
- 2FA。
- 完整自动锁屏策略配置。

### 3.4 客户管理

Phase 1 需要支持门店快速创建客户和找回老客户。

必须交付：

- 新建客户：姓名、手机号、地址、备注。
- 编辑客户基础信息。
- 按手机号、姓名、订单号搜索客户。
- 查看客户历史订单列表。
- 支持老客户快速下单。
- 同手机号重复客户时，至少能展示候选客户供店员选择。

不要求 Phase 1 完整实现：

- 会员等级。
- 积分。
- 生日优惠。
- 沉睡客户召回。
- 推荐奖励。
- 复杂客户画像和营销分析。

### 3.5 服务目录与价格

Phase 1 需要支持门店配置基础服务和价格，支撑 POS 下单。

必须交付：

- 服务分类管理。
- 服务项目 / Article 管理。
- 基础计价方式：按件、按公斤。
- 标准价格配置。
- 服务启用/停用。
- POS 端按分类选择服务。
- 已确认订单不受后续价格修改影响。

不要求 Phase 1 完整实现：

- 个人特殊价。
- 客户分类价。
- 复杂套餐价。
- 大面积计价规则。
- 价格历史报表。

### 3.6 POS 下单与收件

Phase 1 的核心是 POS 下单与收件。

必须交付：

- 创建订单。
- 选择客户。
- 选择服务项目。
- 添加衣物或按公斤洗衣明细。
- 录入数量、重量、颜色、备注、取件日期。
- 记录基础缺陷描述。
- 自动计算订单金额。
- 支持折扣或手动改价，但必须受权限控制并记录原因。
- 订单确认后生成订单号。
- 支持订单修改，但必须记录修改原因和审计日志。

不要求 Phase 1 完整实现：

- 洗车完整接车流程。
- 复杂照片证据链。
- 电子签名。
- 裁缝复杂工序。
- 地毯面积高级计价。
- 多业务对象混合复杂拆单。

### 3.7 订单状态与取件交付

Phase 1 需要支持基础状态追踪。

必须交付：

- 订单主状态：Draft、Received、In Progress、Ready、Delivered、Cancelled。
- 店员可以手动更新状态。
- 支持扫码或搜索订单进入状态更新页面。
- Ready 状态后可进入待取列表。
- 客户取件时可以确认交付。
- Delivered 后订单进入历史记录。
- 取消订单需要权限和原因。

不要求 Phase 1 完整实现：

- 完整生产 Kanban。
- Quality Check / Rework 复杂返工流。
- Partially Delivered 复杂部分交付。
- Reserve 超期保留完整规则。
- 自动储位推荐。

### 3.8 支付与基础财务

Phase 1 需要支持基础收款和日结。

必须交付：

- 现金支付记录。
- Wave / Orange Money 基础支付记录。
- 支付状态：待支付、已支付、待确认、失败。
- 支持订单部分未付或待确认状态。
- 现金支付确认后触发钱箱。
- 支付记录进入订单详情。
- 基础退款或支付修正可暂由 Manager/Owner 权限控制。
- 基础 Z Report：按日期/班次统计现金、移动支付、订单数、退款、折扣。
- 今日营收和支付方式汇总。

不要求 Phase 1 完整实现：

- 自动移动支付扣款。
- 完整支付 webhook。
- TPE/card 深度集成。
- B2B 月结。
- 合并发票。
- VAT 复杂计算。
- 应收账款仪表板。

> **批注：移动支付边界**  
> 若 Phase 1 无法确认 Wave / Orange Money API，可先实现“支付方式记录 + 待确认状态 + 人工确认”，真实自动扣款和回调对账进入 Phase 2。

### 3.9 打印、扫码与钱箱

Phase 1 需要支持试点门店确认型号的核心硬件。

必须交付：

- 80mm 小票打印。
- 衣物标签或袋标签打印。
- 基础重印能力，重印需记录日志。
- USB/Bluetooth HID 扫码枪基础输入。
- 现金支付后触发钱箱。
- 硬件配置页面或配置文件。
- 打印失败时保留待打印任务或提示重试。

不要求 Phase 1 完整实现：

- 所有品牌打印机兼容。
- A4 发票完整模板。
- 客户副屏。
- 传送带 / 自动挂衣接口。
- 蓝牙便携打印完整配送场景。

### 3.10 基础离线能力

Phase 1 至少需要支持网络不稳定时门店不完全停摆。

必须交付：

- 网络中断时，本地可以保存新订单草稿或已确认订单。
- 网络中断时，可以保存客户基础信息。
- 网络中断时，可以打印已保存订单的小票或标签。
- 网络恢复后，可以将本地订单、客户和基础状态同步到服务端。
- 本地创建数据必须使用 ULID，不能依赖服务端自增 ID。
- 每台设备生成并保存稳定 `device_id`。
- 同步失败时展示失败原因和待同步数量。

不要求 Phase 1 完整实现：

- 完整双向同步。
- 多设备同时离线后的复杂冲突合并。
- 离线支付自动扣款。
- 离线库存扣减冲突处理。
- 离线报表完整准确生成。

> **重要边界**  
> Phase 1 的离线目标是保障“断网可继续录单和打印”，不是一次性完成企业级离线协同系统。

### 3.11 基础报表

Phase 1 需要让 Owner / Manager 看到门店基础经营结果。

必须交付：

- 今日订单数。
- 今日营收。
- 按支付方式汇总。
- 待取订单数。
- 进行中订单数。
- 基础 Z Report。
- 按日期筛选订单和收入。

不要求 Phase 1 完整实现：

- 高级 BI。
- N vs N-1。
- 多门店对比。
- 员工绩效深度分析。
- 客户留存分析。
- 利润、库存成本和复杂 VAT 报表。

### 3.12 基础后台

Phase 1 后台需要服务试点门店配置和日常管理。

必须交付：

- SaaS Admin 基础租户管理。
- Tenant Admin 基础门店管理。
- 员工管理。
- 客户查询。
- 服务与价格管理。
- 订单查询。
- 支付记录查询。
- 基础报表。
- 硬件配置入口。
- 通知配置入口。
- 操作日志入口。
- 数据备份入口。

不要求 Phase 1 完整实现：

- 完整营销后台。
- 完整库存后台。
- 完整 HR 后台。
- 完整投诉支持后台。
- 完整订阅计费后台。

### 3.13 语言与本地化

Phase 1 需要支持试点所需的基础语言和本地格式。

必须交付：

- 法语 / 英语基础界面。
- 小票和标签主要字段支持法语/英语。
- 默认货币配置。
- 基础日期和时间格式。

不要求 Phase 1 完整实现：

- 完整多国家本地化。
- 多币种结算。
- 所有报表和营销文案完整多语言。

### 3.14 消息通知基础

Phase 1 需要为订单通知和后续客户运营建立基础配置入口，但不要求完成完整营销自动化。

必须交付：

- Tenant Admin 中提供通知配置入口。
- 支持查看订单创建、订单 Ready、逾期未取、配送通知等模板占位。
- 支持渠道开关占位：WhatsApp、SMS、Email。
- 支持通知发送记录的数据结构和列表入口。
- 通知配置修改必须记录审计日志。

不要求 Phase 1 完整实现：

- WhatsApp/SMS/Email 真实供应商深度接入。
- 模板审核回调。
- 批量营销活动。
- 退订管理。
- 自动客户召回。

### 3.15 日志管理基础

Phase 1 需要让平台方和租户方能查看关键操作与系统异常摘要，便于试点门店排障。

必须交付：

- SaaS Admin 查看平台级审计日志和系统日志摘要。
- Tenant Admin 查看本租户操作日志。
- 记录登录、登出、权限拒绝、用户禁用、价格修改、硬件修改、通知配置修改、备份触发等事件。
- 日志至少支持按时间、操作类型、操作者、租户或门店筛选。
- 日志中敏感字段必须脱敏。

不要求 Phase 1 完整实现：

- 完整 APM。
- 分布式链路追踪。
- 实时告警平台。
- 日志长期归档策略。

### 3.16 数据备份基础

Phase 1 需要提供基础数据备份可见性，保证试点数据有基本恢复通道。

必须交付：

- Tenant Admin 查看本租户最近备份状态。
- SaaS Admin 查看平台级备份任务状态。
- 支持手动触发备份任务或提交备份申请。
- 显示备份状态：pending、running、succeeded、failed。
- 备份任务需记录触发人、时间、范围、结果和失败原因。
- 恢复操作默认走管理员审核或人工流程，不允许普通租户直接恢复生产数据。

不要求 Phase 1 完整实现：

- 跨区域容灾。
- 自动恢复演练。
- 租户自助恢复生产数据。
- 细粒度单表/单订单恢复。
- 完整备份加密和生命周期管理后台。

## 4. Phase 1 明确不交付范围

以下能力不应纳入 Phase 1 验收，除非双方另行确认范围、成本和排期：

| 模块 | Phase 1 不交付内容 |
| ---- | ------------------ |
| **完整 SaaS 计费** | 自动订阅扣费、欠费自动停用、租户付款对账、套餐升级降级。 |
| **完整多门店运营** | 多门店对比、跨门店调拨、跨门店复杂权限、集团级财务。 |
| **会员营销** | 积分、优惠券、生日营销、沉睡客户召回、推荐奖励、Google 评价引导。 |
| **B2B 月结** | 信用额度、对账单、合并发票、应收账款、逾期催收。 |
| **配送取送** | 预约日历、配送员任务、GPS、ETA、配送费用、便携打印完整流程。 |
| **库存采购** | 库存流水、供应商、采购单、零售库存扣减、机器维护。 |
| **员工 HR** | 排班、打卡、绩效、工资、预支。 |
| **投诉满意度** | 投诉工单、证据链、赔付审批、满意度调查。 |
| **高级报表** | 高级 BI、N vs N-1、利润、客户留存、预测报表。 |
| **AI** | 污渍识别、面料风险、需求预测、智能排程。 |
| **高级硬件** | 客户副屏、传送带、自动挂衣、未确认型号设备兼容。 |
| **完整通知平台** | 真实供应商深度集成、模板审核、批量营销、退订管理、自动召回。 |
| **完整运维平台** | APM、分布式追踪、实时告警、长期日志归档、自动恢复演练。 |
| **开放 API / 白标** | 第三方开放 API、白标、多品牌独立配置。 |
| **培训平台** | 视频课程、PDF、测验、证书和长期在线培训平台。 |

## 5. Phase 1 待确认事项

| 待确认事项 | 建议处理方式 |
| ---------- | ------------ |
| **试点门店数量** | 默认 Phase 1 支持 1 个租户、1 个试点门店；多门店进入 Phase 2。 |
| **硬件型号** | 客户需提供明确型号、连接方式、驱动/SDK 和测试设备。 |
| **Wave / Orange Money API** | 若 API 未确认，Phase 1 先做人工确认式支付记录。 |
| **离线范围** | Phase 1 只承诺断网录单、打印和恢复后上传，不承诺复杂冲突合并。 |
| **标签模板** | 需要确认标签纸尺寸、打印机类型、字段内容和语言。 |
| **小票模板** | 需要确认门店信息、税务字段、支付字段、客户签名字段是否需要。 |
| **上线语言** | 默认法语 + 英语基础界面，其他语言后置。 |
| **真实数据导入** | 若需导入历史客户或价格表，需单独确认数据格式和清洗责任。 |
| **通知渠道供应商** | 若 Phase 1 要真实发送 WhatsApp/SMS/Email，需要确认供应商、模板审核、费用和测试账号。 |
| **备份保留策略** | 需要确认备份保留天数、可恢复范围、恢复审批人和数据责任边界。 |

## 6. Phase 1 验收标准

### 6.1 验收原则

Phase 1 验收以真实门店可营业为核心，不以高级功能完整度为核心。

验收必须满足：

- 核心营业流程可完成。
- 核心数据可追溯。
- 核心硬件可使用。
- 核心支付记录可查询。
- 核心报表可生成。
- 权限和审计覆盖敏感操作。

### 6.2 准入条件

进入正式验收前，应满足：

- 试点租户和门店已创建。
- 至少 1 个 Owner、1 个 Manager、1 个 Cashier 可登录。
- 基础服务和价格已配置。
- 打印机、扫码枪、钱箱等确认硬件已连接并完成测试。
- 测试支付方式已配置。
- 法语/英语基础界面可使用。
- 测试环境或试点环境数据已准备。

### 6.3 验收场景

#### 场景 1：新客户到店下单

步骤：

1. Cashier 登录 POS。
2. 创建新客户，录入姓名和手机号。
3. 新建订单。
4. 添加 3 件衣物服务。
5. 录入颜色、备注、取件日期。
6. 系统自动计算金额。
7. 客户确认订单。

通过标准：

- 客户创建成功。
- 订单号生成成功。
- 订单金额正确。
- 订单状态为 Received。
- 订单归属正确租户、门店和操作人。

#### 场景 2：老客户快速找单

步骤：

1. Cashier 使用手机号或姓名搜索客户。
2. 系统展示客户档案和历史订单。
3. 基于该客户创建新订单。

通过标准：

- 能正确找到客户。
- 能看到历史订单。
- 新订单正确关联该客户。

#### 场景 3：按公斤洗衣下单

步骤：

1. 选择客户。
2. 选择按公斤洗衣服务。
3. 输入重量和袋数。
4. 系统计价。
5. 确认订单。

通过标准：

- 重量和袋数保存成功。
- 价格计算正确。
- 小票或标签包含必要信息。

#### 场景 4：现金支付与钱箱

步骤：

1. 订单确认后选择现金支付。
2. 输入收款金额。
3. 确认支付。
4. 系统触发钱箱。
5. 打印小票。

通过标准：

- 支付状态为已支付。
- 钱箱被正确触发。
- 小票打印成功。
- 支付记录进入订单详情和 Z Report。

#### 场景 5：移动支付待确认

步骤：

1. 订单确认后选择 Wave 或 Orange Money。
2. 系统记录支付方式和金额。
3. 若未接入自动 API，标记为待确认。
4. Manager 或授权用户人工确认支付。

通过标准：

- 支付记录生成。
- 待确认状态可见。
- 人工确认后订单支付状态更新。
- 操作人和时间被记录。

#### 场景 6：打印小票和标签

步骤：

1. 订单确认后打印客户小票。
2. 打印衣物标签或袋标签。
3. 重新打印一次标签。

通过标准：

- 小票字段正确。
- 标签字段正确。
- 重印成功。
- 重印操作进入审计日志。

#### 场景 7：扫码查单与状态更新

步骤：

1. 使用扫码枪扫描订单号或标签。
2. 系统打开对应订单。
3. 将状态从 Received 更新为 In Progress。
4. 再更新为 Ready。

通过标准：

- 扫码可以定位订单。
- 状态更新成功。
- 状态历史记录操作人、设备和时间。

#### 场景 8：客户取件交付

步骤：

1. Cashier 搜索客户或订单。
2. 打开 Ready 订单。
3. 确认客户取件。
4. 将订单更新为 Delivered。

通过标准：

- 订单状态变为 Delivered。
- 交付时间和操作人被记录。
- 已交付订单进入历史记录。

#### 场景 9：断网录单与恢复同步

步骤：

1. POS 断开网络。
2. 创建客户和订单。
3. 打印小票或标签。
4. 恢复网络。
5. 系统同步本地订单到服务端。

通过标准：

- 断网时可保存订单。
- 断网时可打印。
- 恢复网络后同步成功。
- 服务端数据不重复。
- 同步失败时可看到失败原因。

#### 场景 10：基础 Z Report

步骤：

1. 创建多笔订单，覆盖现金和移动支付。
2. 执行若干订单状态更新。
3. 生成当日 Z Report。

通过标准：

- Z Report 展示订单数。
- 展示现金金额。
- 展示移动支付金额。
- 展示退款/折扣字段，若无数据则为 0。
- Z Report 与订单支付记录可追溯。

#### 场景 11：权限控制

步骤：

1. Cashier 尝试删除订单。
2. Cashier 尝试修改价格。
3. Manager 或 Owner 执行授权操作。

通过标准：

- Cashier 无权执行敏感操作。
- 授权用户可执行。
- 敏感操作记录原因和审计日志。

#### 场景 12：后台基础配置

步骤：

1. Owner / Manager 登录后台。
2. 新增或编辑服务项目。
3. 修改价格。
4. 新增员工。
5. 禁用员工。

通过标准：

- 配置保存成功。
- POS 可看到启用服务。
- 禁用员工无法登录。
- 价格修改不影响已确认订单。

#### 场景 13：通知配置与发送记录

步骤：

1. Owner / Manager 打开通知配置页面。
2. 查看订单 Ready 通知模板。
3. 修改通知渠道开关或模板占位内容。
4. 查看通知发送记录列表。

通过标准：

- 通知配置可以保存。
- 修改操作写入审计日志。
- 发送记录列表可展示状态、渠道、关联订单和失败原因。
- 页面明确标识真实供应商发送能力是否已接入。

#### 场景 14：操作日志与数据备份

步骤：

1. Owner / Manager 打开操作日志页面。
2. 按时间或操作类型筛选日志。
3. 打开数据备份页面。
4. 查看最近备份状态。
5. 触发手动备份或提交备份申请。

通过标准：

- 操作日志可按权限查看。
- 敏感字段已脱敏。
- 备份任务创建成功或申请提交成功。
- 可查看备份状态和失败原因。
- 恢复生产数据不会由普通租户直接执行。

## 7. 验收输出物

Phase 1 验收完成后，应形成以下输出物：

- Phase 1 验收测试记录。
- 已通过验收场景清单。
- 未通过或遗留问题清单。

- 支付测试记录。
- 离线测试记录。

- 日志与备份测试记录。
- 上线配置记录。
- 客户培训记录。
- Phase 1 验收签收单。

## 8. Phase 1 通过标准

Phase 1 可以判定为通过，当且仅当：

1. 所有 P0 验收场景通过。
2. 不存在阻塞门店营业的严重缺陷。
3. 核心硬件在确认型号范围内可用。
4. 核心支付记录和 Z Report 可追溯。
5. 断网录单、打印和恢复后同步的基础能力通过测试。
6. 业务方确认 Phase 1 不包含的功能不会阻塞试点营业。

> **最终判断口径**  
> Phase 1 的验收重点是“试点门店能否稳定营业”，不是“CleanHub 完整平台是否全部完成”。

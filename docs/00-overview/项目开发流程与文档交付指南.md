# 项目开发流程与文档交付指南

> 适用对象：产品经理、项目经理、研发负责人、UI/UX、测试、实施、运维、业务方。  
> 适用项目：Web / App / SaaS / POS / 多终端 / 支付 / 硬件 / 离线 / 企业级系统。  
> 参考口径：本文参考全球成熟研发团队常见实践，但不声称代表 OpenAI、Anthropic、Google、Tencent、ByteDance 等公司的内部流程。

---

## 1. 核心结论

一个规范项目不是一上来就写代码，也不是只写一份 PRD 就够。成熟团队通常会把项目推进分成几个阶段：

1. **项目接触与需求发现**
2. **产品定义与范围确认**
3. **设计与技术方案准备**
4. **项目计划与任务拆解**
5. **研发、测试与验收**
6. **上线、实施与运营支持**

但这不代表每个项目都要准备几十份文档。正确做法是：

- **小项目少文档，重执行。**
- **中型项目有核心文档，保证对齐。**
- **大型或高风险项目必须文档完整，保证可控、可追溯、可验收。**

CleanHub 这类项目涉及 **多租户、POS、移动端、桌面端、离线同步、支付、硬件、财务、配送、培训、实施**，属于高复杂度项目，不能只靠一份 PRD 推进。

---

## 2. 项目文档分层

项目文档可以分为五层：

| 层级 | 主要回答的问题 | 典型负责人 | 主要使用者 |
| ---- | -------------- | ---------- | ---------- |
| **业务与产品层** | 为什么做、给谁用、做什么、不做什么 | 产品经理 | 业务方、项目经理、研发、UI、测试 |
| **项目管理层** | 谁来做、什么时候做、风险是什么、如何协作 | 项目经理 | 业务方、产品、研发、测试、实施 |
| **设计体验层** | 用户怎么操作、页面怎么组织、交互怎么走 | UI/UX | 产品、研发、测试、业务方 |
| **技术实现层** | 系统怎么设计、接口怎么定义、数据怎么流转 | 技术负责人 / 架构师 | 研发、测试、运维、安全 |
| **测试交付层** | 怎么验证、怎么上线、怎么培训、怎么支持 | 测试 / 实施 / 运维 | 项目经理、产品、研发、客户 |

## 3. 产品经理需要准备的材料

### 3.1 产品经理完整材料清单

| 文档 | 是否核心 | 主要用途 | 主要使用者 |
| ---- | -------- | -------- | ---------- |
| **项目背景与问题定义** | 核心 | 说明为什么要做、业务痛点是什么 | 业务方、项目经理、产品、研发 |
| **PRD 产品需求文档** | 核心 | 定义产品目标、用户、范围、功能模块、非功能需求 | 所有人 |
| **Scope 范围说明书** | 核心 | 明确做什么、不做什么、后续做什么、待确认什么 | 业务方、项目经理、研发、测试 |
| **Phase 阶段计划** | 核心 | 定义 Phase 1/2/3 的目标、范围、验收口径 | 项目经理、业务方、研发 |
| **用户角色与权限说明** | 核心 | 明确各类角色的权限边界 | 研发、测试、UI、业务方 |
| **用户流程图** | 核心 | 说明关键业务流程如何发生 | UI、研发、测试、业务方 |
| **页面清单 / 信息架构** | 核心 | 明确每个端有哪些页面和入口 | UI、研发、项目经理 |
| **验收标准** | 核心 | 定义什么叫完成、什么叫验收通过 | 项目经理、测试、业务方、研发 |
| **Backlog / Epic / User Story 初稿** | 核心 | 把需求转成可估时、可排期、可开发的条目 | 项目经理、研发、测试 |
| **数据字典概览** | 建议核心 | 说明核心业务对象和关系 | 研发、测试、数据、项目经理 |
| **非功能性需求** | 建议核心 | 定义性能、安全、离线、可用性、审计等要求 | 研发、测试、运维 |
| **第三方依赖清单** | 中高复杂度核心 | 明确支付、短信、硬件、AI、地图等外部依赖 | 项目经理、研发、测试 |
| **风险与待确认事项清单** | 核心 | 提前暴露范围、技术、合同、第三方风险 | 业务方、项目经理、产品、研发 |
| **指标与成功标准** | 建议核心 | 定义项目上线后如何判断成功 | 业务方、产品、项目经理 |
| **上线与运营目标** | 中大型项目需要 | 定义试点、推广、培训、支持目标 | 项目经理、实施、业务方 |

### 3.2 产品经理最核心的 7 份材料

如果时间有限，产品经理最少应先准备这 7 份：

1. **PRD 产品需求文档**
2. **Phase 1 范围与验收标准**
3. **用户流程与页面清单**
4. **权限矩阵**
5. **非功能需求与关键技术约束**
6. **风险与待确认事项清单**
7. **Backlog / Epic / User Story 初稿**

对于 CleanHub，还应优先追加：

1. **离线同步专题需求**
2. **支付财务专题需求**
3. **硬件验收清单**

因为这三个是 CleanHub 的高风险核心。

## 4. 项目经理需要准备的材料

产品经理给出产品材料后，项目经理需要把“产品需求”转换成“可管理的项目计划”。

### 4.1 项目经理完整材料清单

| 文档 | 是否核心 | 主要用途 | 主要使用者 |
| ---- | -------- | -------- | ---------- |
| **项目章程 Project Charter** | 中大型项目核心 | 明确项目目标、范围、负责人、成功标准 | 业务方、管理层、项目团队 |
| **项目范围基线 Scope Baseline** | 核心 | 固化本期范围和变更规则 | 业务方、产品、研发、测试 |
| **WBS 工作分解结构** | 核心 | 把项目拆成可执行工作包 | 项目经理、研发负责人 |
| **里程碑计划 Milestone Plan** | 核心 | 明确每阶段交付时间和门禁 | 所有人 |
| **资源计划 Resource Plan** | 核心 | 明确需要哪些角色、多少人、投入周期 | 管理层、研发负责人 |
| **RACI 责任矩阵** | 中大型项目核心 | 明确谁负责、谁审批、谁参与、谁知会 | 所有人 |
| **风险/问题/依赖清单 RAID Log** | 核心 | 管理风险、问题、假设和外部依赖 | 项目经理、产品、研发、业务方 |
| **沟通计划 Communication Plan** | 中大型项目需要 | 明确会议节奏、汇报对象、升级机制 | 所有人 |
| **变更管理流程 Change Control** | 合同项目核心 | 管理需求新增、范围变更和延期影响 | 业务方、项目经理、产品 |
| **发布计划 Release Plan** | 核心 | 明确版本、灰度、上线、回滚安排 | 研发、测试、运维、业务方 |
| **项目状态周报** | 核心 | 跟踪进度、风险、阻塞和决策 | 业务方、管理层、项目团队 |
| **验收与交付计划** | 核心 | 明确 UAT、试运行、签收、培训和交付物 | 业务方、测试、实施 |

### 4.2 项目经理最核心的 6 份材料

如果项目刚启动，项目经理至少需要：

1. **项目范围基线**
2. **WBS 工作分解结构**
3. **里程碑计划**
4. **RACI 责任矩阵**
5. **RAID 风险/问题/依赖清单**
6. **发布与验收计划**

## 5. 研发负责人需要准备的材料

项目经理不直接写技术开发文档。通常是项目经理负责组织和跟踪，**技术负责人 / 架构师 / Tech Lead** 负责产出技术方案。

### 5.1 技术侧完整材料清单

| 文档 | 是否核心 | 主要用途 | 主要使用者 |
| ---- | -------- | -------- | ---------- |
| **技术方案总览 Technical Design** | 核心 | 说明整体架构、技术选型、模块边界 | 研发、项目经理、测试 |
| **系统架构图** | 核心 | 展示前端、后端、数据库、队列、第三方依赖关系 | 研发、测试、运维 |
| **数据模型设计 / ERD** | 核心 | 定义表、关系、索引、约束、审计字段 | 后端、测试、数据 |
| **API 设计文档** | 核心 | 定义接口、请求响应、错误码、鉴权 | 前端、后端、测试 |
| **权限与安全设计** | 核心 | 定义 RBAC、RLS、审计、加密、会话策略 | 后端、安全、测试 |
| **离线同步技术方案** | 高风险项目核心 | 定义本地库、同步队列、冲突、幂等、设备 ID | 前端、后端、测试 |
| **支付与财务技术方案** | 高风险项目核心 | 定义支付状态机、回调、对账、退款、Z Report | 后端、测试、财务业务方 |
| **硬件集成方案** | 硬件项目核心 | 定义打印、扫码、钱箱、TPE、蓝牙、驱动边界 | 桌面端、移动端、测试、实施 |
| **部署与环境方案** | 核心 | 定义 dev/staging/prod、CI/CD、环境变量、迁移 | DevOps、研发、测试 |
| **日志与监控方案** | 中大型项目核心 | 定义日志、告警、追踪、错误监控 | 研发、运维、支持 |
| **性能与容量设计** | 中大型项目需要 | 定义并发、数据量、缓存、队列、报表策略 | 后端、架构、运维 |
| **ADR 架构决策记录** | 建议 | 记录关键技术选择和取舍 | 研发、未来维护团队 |

### 5.2 技术侧最核心的 7 份材料

对一个正式项目，研发侧至少需要：

1. **技术方案总览**
2. **系统架构图**
3. **数据模型设计**
4. **API 设计文档**
5. **权限与安全设计**
6. **部署与环境方案**
7. **测试配合说明**

对 CleanHub 必须额外补充：

1. **离线同步技术方案**
2. **支付与财务技术方案**
3. **硬件集成方案**

## 6. UI/UX 需要准备的材料

UI/UX 的工作不是只画好看的页面，而是把用户流程变成可用、可学习、可落地的操作体验。

### 6.1 UI/UX 文档清单

| 文档 | 是否核心 | 主要用途 | 主要使用者 |
| ---- | -------- | -------- | ---------- |
| **设计目标与原则** | 建议核心 | 明确产品体验方向和设计约束 | 产品、UI、研发 |
| **用户流程图** | 核心 | 展示用户从开始到完成任务的路径 | UI、产品、研发、测试 |
| **信息架构 / 导航结构** | 核心 | 明确菜单、页面层级和入口 | UI、前端、产品 |
| **页面清单** | 核心 | 明确每个端需要哪些页面 | UI、前端、项目经理 |
| **低保真线框图** | 核心 | 快速确认布局和流程 | 产品、业务方、研发 |
| **高保真设计稿** | 核心 | 用于前端开发和客户确认 | 前端、产品、业务方 |
| **交互原型** | 中大型项目核心 | 验证复杂流程和操作路径 | 产品、业务方、测试 |
| **设计系统 / 组件规范** | 中大型项目核心 | 保证多页面、多端一致性 | UI、前端 |
| **切图/标注/状态说明** | 核心 | 帮助前端准确实现 | 前端 |
| **文案与多语言表** | 国际化项目核心 | 管理按钮、提示、错误信息和多语言 | UI、产品、前端、测试 |

### 6.2 UI 最核心的 5 份材料

1. **用户流程图**
2. **信息架构 / 页面清单**
3. **低保真线框图**
4. **高保真设计稿**
5. **设计系统 / 组件规范**

## 7. 测试团队需要准备的材料

测试不是开发完成后才开始。成熟团队会让测试在 PRD 和技术方案阶段就参与，提前定义验收方法。

### 7.1 测试文档清单

| 文档 | 是否核心 | 主要用途 | 主要使用者 |
| ---- | -------- | -------- | ---------- |
| **测试策略 Test Strategy** | 核心 | 明确测试范围、类型、环境和风险 | 测试、项目经理、研发 |
| **测试计划 Test Plan** | 核心 | 明确测试周期、人员、环境、准入准出标准 | 项目经理、测试、研发 |
| **测试用例 Test Cases** | 核心 | 覆盖功能、异常、权限、边界和回归 | 测试、研发 |
| **验收测试 UAT Cases** | 核心 | 给业务方验收使用 | 业务方、产品、测试 |
| **缺陷管理规范** | 建议 | 统一缺陷等级、流转、关闭规则 | 测试、研发、项目经理 |
| **回归测试清单** | 核心 | 每次发布前检查核心链路 | 测试、研发 |
| **性能测试报告** | 复杂项目需要 | 验证并发、响应时间和稳定性 | 研发、运维、项目经理 |
| **安全测试清单** | 涉及支付/隐私核心 | 验证权限、越权、敏感信息、审计 | 测试、安全、研发 |
| **硬件测试报告** | 硬件项目核心 | 验证打印机、扫码枪、钱箱、TPE 等 | 测试、实施、研发 |
| **上线验收报告** | 核心 | 记录最终测试结论和遗留问题 | 项目经理、业务方 |

### 7.2 测试最核心的 5 份材料

1. **测试策略**
2. **测试计划**
3. **测试用例**
4. **UAT 验收用例**
5. **回归测试清单**

对 CleanHub 必须额外补充：

1. **离线测试用例**
2. **支付测试用例**
3. **硬件测试用例**
4. **多租户/权限测试用例**

## 8. 实施、运维和支持需要准备的材料

涉及真实客户上线的系统，不能只交代码。必须能安装、培训、上线、排障、维护。

### 8.1 实施与运维文档清单

| 文档 | 是否核心 | 主要用途 | 主要使用者 |
| ---- | -------- | -------- | ---------- |
| **上线计划 Go-live Plan** | 核心 | 明确上线步骤、时间、负责人、回滚方案 | 项目经理、实施、研发、业务方 |
| **部署手册** | 核心 | 说明环境、配置、数据库迁移、服务启动 | 运维、研发 |
| **运行手册 Runbook** | 中大型项目核心 | 说明常见故障处理、告警响应和恢复步骤 | 运维、支持 |
| **硬件安装手册** | 硬件项目核心 | 指导打印机、扫码枪、钱箱、设备连接 | 实施、技术员 |
| **客户培训材料** | 核心 | 教门店员工和管理员使用系统 | 实施、客户、支持 |
| **管理员手册** | 核心 | 教 Owner / Manager 管理后台配置 | 客户、支持 |
| **支持流程与升级机制** | 核心 | 定义 Level 1/2/3 支持边界 | 支持、项目经理、研发 |
| **发布说明 Release Notes** | 核心 | 告知变更、新功能、修复和风险 | 客户、支持、项目团队 |
| **验收签收单** | 合同项目核心 | 记录客户确认交付结果 | 项目经理、业务方 |

## 9. 什么时候需要全部文档，什么时候只需要部分文档

### 9.1 需要完整文档体系的项目

以下情况建议准备比较完整的文档体系：

- 合同金额较大，且有明确验收责任。
- 涉及支付、财务、隐私、安全、审计。
- 涉及硬件、线下实施、门店培训。
- 涉及多端、多团队、多供应商协作。
- 涉及离线、同步、复杂数据一致性。
- 涉及政府、金融、医疗、企业级客户。
- 需求来源复杂，存在合同、客户、销售、技术之间的范围冲突。
- 项目失败成本很高，返工代价很大。

CleanHub 属于这一类，因此至少需要核心文档齐全。

### 9.2 可以部分文档的项目

以下情况可以简化文档：

- 内部工具、小范围使用、低风险。
- 单一页面或单一功能迭代。
- 无支付、无隐私、无硬件、无复杂权限。
- 一个小团队独立开发，沟通成本低。
- 需求稳定，业务方和研发已经高度熟悉领域。

这类项目通常只需要：

- 简版 PRD
- 页面草图或设计稿
- Backlog
- 验收标准
- 简单测试清单

## 10. 阶段门禁与交付物

成熟团队通常不会等所有文档都完美后才开始，而是采用阶段门禁。

### Gate 0：项目立项前

目标：确认项目是否值得做。

需要材料：

- 项目背景与问题定义
- 初步业务目标
- 初步范围
- 关键风险
- 初步成本和收益判断

通过标准：

- 业务方确认问题真实存在。
- 决策人确认项目值得进入需求阶段。

### Gate 1：需求确认前

目标：确认做什么、不做什么。

需要材料：

- PRD
- Scope 范围说明
- 用户角色
- 核心流程
- Phase 初步计划
- 风险与待确认事项

通过标准：

- 业务方、产品、项目经理、研发负责人对范围有共同理解。
- 高风险问题已有负责人和确认计划。

### Gate 2：设计与技术方案确认前

目标：确认能不能做、怎么做。

需要材料：

- 页面清单
- 用户流程
- 低保真或高保真原型
- 技术方案总览
- 数据模型概览
- API 初稿
- 权限矩阵
- 非功能需求

通过标准：

- 研发能估时。
- UI 能出完整设计。
- 测试能写用例。
- 项目经理能排计划。

### Gate 3：开发启动前

需要材料：

## 12. 推荐的最合适流程

以下流程适合 CleanHub 这种复杂项目：

### Step 1：产品总 PRD

目标：统一业务目标和完整产品范围。

产出：

- 产品总 PRD
- 核心模块
- 非功能需求
- 数据字典概览
- Phase 初步计划
- 待确认事项

### Step 2：Phase 1 范围与验收标准

目标：把完整产品范围收敛到第一阶段可交付闭环。

产出：

- Phase 1 In Scope
- Phase 1 Out of Scope
- Phase 1 验收场景
- Phase 1 风险清单

### Step 3：用户流程与页面清单

目标：把产品模块转成用户能操作的页面和流程。

产出：

- SaaS Admin 页面清单
- Tenant Admin 页面清单
- POS 页面清单
- Mobile 页面清单
- Desktop 能力清单
- 核心用户流程图

### Step 4：专题需求

目标：把高风险领域单独讲清楚。

CleanHub 优先专题：

- 权限矩阵
- 离线同步需求
- 支付财务需求
- 硬件验收清单

### Step 5：设计与技术方案

目标：让 UI 能设计，让研发能估时。

产出：

- 低保真 / 高保真设计
- 技术方案
- API 初稿
- 数据模型
- 架构图

### Step 6：项目计划与 Backlog

目标：让项目进入可执行状态。

产出：

- WBS
- 里程碑计划
- Backlog
- Sprint 计划
- 风险/依赖清单

### Step 7：开发、测试、验收、上线

目标：按阶段交付并真实上线。

产出：

- 测试用例
- UAT 用例
- 发布计划
- 上线清单
- 培训材料
- 验收签收单

## 13. CleanHub 当前建议

CleanHub 当前已经有一份产品总 PRD。下一步不建议继续无限扩写 PRD，而应拆出执行材料。

研发负责人也可以开始做：

## 14. 最终判断

顶级团队的标准不是“文档越多越专业”，而是：

- 每份文档都有明确用途。
- 每份文档都有明确负责人。
- 每份文档都有明确使用者。
- 每份文档能帮助减少返工、降低风险、加快决策。
- 文档能服务交付，而不是拖慢交付。

因此，最合适的流程是：

**先用产品总 PRD 对齐方向，再用范围、流程、权限、专题需求和 Backlog 支撑执行；项目经理基于这些材料制定计划；研发基于这些材料做技术方案；UI 基于这些材料出设计；测试基于这些材料写用例；实施基于这些材料上线和培训。**
